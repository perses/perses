# Upgrading from v0.55.0 to v0.56.0

This document provides instructions for upgrading Perses specially when dealing with breaking changes. As Perses is a
rapidly evolving project, it's important to keep your installation up to date to benefit from the latest features and
improvements.

Then, upgrading Perses is also depending on your usage as Perses can be used in different ways (e.g. as a standalone
application, as a library, etc.). Therefore, the upgrade process may vary based on your specific use case.

## Perses application

### Deprecated configuration fields are removed

The following configuration fields were deprecated in previous releases and are now removed:

| Removed field                                         | Replacement                                                             |
|-------------------------------------------------------|-------------------------------------------------------------------------|
| `schemas`                                             | None, remove it from your config                                        |
| `ephemeral_dashboards_cleanup_interval`               | `ephemeral_dashboard.enable` and `ephemeral_dashboard.cleanup_interval` |
| `security.authorization.check_latest_update_interval` | `security.authorization.provider.native.check_latest_update_interval`   |
| `security.authorization.guest_permissions`            | `security.authorization.provider.native.guest_permissions`              |
| `plugin.archive_path`                                 | `plugin.archive_paths` (a list)                                         |

The configuration file is parsed strictly: **Perses refuses to start** if one of these fields is still present in your
configuration file. Update it before upgrading:

```yaml
# Before
schemas:
  panels_path: "schemas/panels"
  queries_path: "schemas/queries"
  datasources_path: "schemas/datasources"
  variables_path: "schemas/variables"
ephemeral_dashboards_cleanup_interval: 2h
security:
  authorization:
    check_latest_update_interval: 1m
    guest_permissions:
      - actions:
          - read
        scopes:
          - "*"
plugin:
  archive_path: /etc/perses/plugins-archive

# After
ephemeral_dashboard:
  enable: true
  cleanup_interval: 2h
security:
  authorization:
    provider:
      native:
        check_latest_update_interval: 1m
        guest_permissions:
          - actions:
              - read
            scopes:
              - "*"
plugin:
  archive_paths:
    - /etc/perses/plugins-archive
```

If you configure Perses with environment variables, the variables matching the removed fields are now **silently
ignored**. In particular, the guest permissions would no longer be applied, the ephemeral dashboards would no longer be
enabled, and the plugin archives would be looked up in the default folder. Rename them accordingly:

```txt
PERSES_EPHEMERAL_DASHBOARDS_CLEANUP_INTERVAL              -> PERSES_EPHEMERAL_DASHBOARD_ENABLE=true
                                                             PERSES_EPHEMERAL_DASHBOARD_CLEANUP_INTERVAL
PERSES_SECURITY_AUTHORIZATION_CHECK_LATEST_UPDATE_INTERVAL -> PERSES_SECURITY_AUTHORIZATION_PROVIDER_NATIVE_CHECK_LATEST_UPDATE_INTERVAL
PERSES_SECURITY_AUTHORIZATION_GUEST_PERMISSIONS_*         -> PERSES_SECURITY_AUTHORIZATION_PROVIDER_NATIVE_GUEST_PERMISSIONS_*
PERSES_PLUGIN_ARCHIVE_PATH                                -> PERSES_PLUGIN_ARCHIVE_PATHS_0
PERSES_SCHEMAS_*                                          -> (remove)
```

#### Go configuration API

If you use the Go package `github.com/perses/perses/pkg/model/api/config` directly, the corresponding types and fields
are removed as well:

- The type `Schemas` and the constants `DefaultPanelsPath`, `DefaultQueriesPath`, `DefaultDatasourcesPath` and
  `DefaultVariablesPath` are removed, as well as the field `Config.Schemas`.
- The field `Config.EphemeralDashboardsCleanupInterval` is removed. Use `Config.EphemeralDashboard` instead.
- The fields `AuthorizationConfig.CheckLatestUpdateInterval` and `AuthorizationConfig.GuestPermissions` are removed, as
  well as the method `AuthorizationConfig.Verify()`. Use `AuthorizationConfig.Provider.Native` instead.
- The field `Plugin.ArchivePath` is removed. Use `Plugin.ArchivePaths` instead:

  ```go
  // Before
  config.Plugin{ArchivePath: "plugins-archive"}

  // After
  config.Plugin{ArchivePaths: []string{"plugins-archive"}}
  ```

### A secret using `authorization` must define its credentials

An `authorization` block in a Secret or a GlobalSecret must now set `credentials` or `credentialsFile`, as `basicAuth`
and `oauth` already require their own secret. Previously, an `authorization` block without any credentials was accepted
and the datasource requests were sent with an empty `Authorization` header. Such a secret is now refused when it is
saved, and it can no longer be read once Perses is upgraded (the datasources using it then fail).

Before upgrading, set the credentials, or remove the `authorization` block if the datasource does not need any
authentication:

```yaml
# Before
kind: Secret
spec:
  authorization:
    type: Bearer

# After
kind: Secret
spec:
  authorization:
    type: Bearer
    credentials: "<token>"
```

The same rule applies to the `authorization` block of the HTTP service discovery (`datasource.global.discovery[].http_sd`)
in the Perses configuration file: as the configuration file is parsed strictly, **Perses refuses to start** if this block
doesn't set its credentials.

It also applies to the `authorization` block of the `percli` configuration file (`~/.perses/config` by default).
If this file contains an `authorization` block without credentials, `percli` can no longer read it and behaves as if
you were not logged in: run `percli login` again to store a valid token, or remove the block from the file.

### HTTP metrics are renamed

The metrics of the HTTP server are renamed to follow the Prometheus naming conventions:

| Before                                | After                                  |
|---------------------------------------|----------------------------------------|
| `perses_http_request_total`           | `perses_http_requests_total`           |
| `perses_http_request_duration_second` | `perses_http_request_duration_seconds` |

The series of the summary are renamed accordingly (e.g. `perses_http_request_duration_second_count` becomes
`perses_http_request_duration_seconds_count`). Update the dashboards, recording rules and alerts using them.

### TLS configuration of the HTTP server

- **Perses refuses to start** when only one of `--web.tls-cert-file` and `--web.tls-key-file` is set. Previously, it
  silently started in plain HTTP. Set both flags to serve HTTPS, or none of them to serve HTTP.
- `--web.tls-min-version`, `--web.tls-max-version` and `--web.tls-cipher-suites` were ignored, they are now applied.
  Check that your clients support the TLS versions and cipher suites you set.
- The certificate and the key are reloaded when the files change, so Perses no longer needs to be restarted when they
  are rotated.

### Other changes of the HTTP server

- When the HTTP server fails to start or stops unexpectedly (for example, when the address is already in use), Perses
  now exits with the status code `1` instead of `0`. A service manager restarting Perses only on failure (like systemd
  with `Restart=on-failure`) now restarts it.
- The connections that don't send their request headers within 10 seconds are closed, as well as the idle keep-alive
  connections after 2 minutes.
- The `uri` field of the access logs no longer contains the query string, as it can contain sensitive data (tokens,
  OAuth codes, etc.).

### CORS configuration

- **Perses refuses to start** when `security.cors.allow_credentials` is `true` while `security.cors.allow_origins`
  contains `*` or is not set (its default value is `["*"]`). The browsers reject the requests with credentials when
  every origin is allowed, so this configuration never worked for them. List the allowed origins instead.
- The wildcard patterns in `security.cors.allow_origins`, where `*` matches 0 or more characters and `?` matches 1
  character (e.g. `https://*.example.com`), are **deprecated and will be removed in v0.58.0**. They still work in this
  release, but Perses logs a warning at startup for each of them. They are easy to get wrong: for example,
  `https://*example.com` also allows `https://evilexample.com`. Replace them with the list of the exact origins
  allowed (`*` alone is not a pattern and remains supported). See
  [#4721](https://github.com/perses/perses/issues/4721).

```yaml
# Before
security:
  cors:
    enable: true
    allow_origins:
      - "https://*.example.com"

# After
security:
  cors:
    enable: true
    allow_origins:
      - "https://grafana.example.com"
      - "https://portal.example.com"
```

## Plugin developer

### React 19 is supported

The Perses npm packages (`@perses-dev/client`, `@perses-dev/components`, `@perses-dev/plugin-system`,
`@perses-dev/dashboards`, `@perses-dev/explore`) and the official plugins now accept `react` and `react-dom`
`^18.3.0 || ^19.0.0` as peer dependencies. Widen the React peer dependencies and the Module Federation `requiredVersion`
of `react` and `react-dom` of your plugin the same way to support both versions.

### The Perses application runs on React 19

The Perses application now runs on React 19 and shares `react/jsx-runtime` with the plugins as a singleton, alongside
`react` and `react-dom`. A plugin bundling its own React 18 JSX runtime crashes on a React 19 host: add
`react/jsx-runtime` to the Module Federation `shared` configuration of your plugin and rebuild it:

```ts
shared: {
  react: { requiredVersion: '^18.3.0 || ^19.0.0', singleton: true },
  'react/jsx-runtime': { requiredVersion: '^18.3.0 || ^19.0.0', singleton: true },
  'react-dom': { requiredVersion: '^18.3.0 || ^19.0.0', singleton: true },
  // ...
},
```

In dev mode (e.g. `percli plugin start`), the default JSX transform imports `react/jsx-dev-runtime`, which the Perses
application doesn't share: the plugin then bundles its own React 18 development runtime and crashes the same way. With
Rsbuild, compile JSX to `react/jsx-runtime` in dev mode as well:

```ts
pluginReact({
  reactCompiler: { target: '18' },
  swcReactOptions: { development: false },
}),
```

Keep compiling your plugin with the React Compiler target `18` so it still runs on React 18 hosts (e.g. applications
embedding Perses).

### `@mui/system` is a peer dependency of `@perses-dev/components`

Install `@mui/system` (`^6.1.10`, matching your `@mui/material` version) if your package manager doesn't install peer
dependencies automatically.

### `use-resize-observer` v10 is required

`use-resize-observer` is upgraded from `^9` to `^10` (v9 doesn't support React 19). The Perses application shares v10
only with the plugins (`requiredVersion: '^10.0.0'`), so a plugin still built against v9 can no longer use it. Upgrade it
in your plugin:

- Bump `use-resize-observer` to `^10.0.0` in your `package.json` and, if your plugin shares it with Module Federation,
  set its `requiredVersion` to `^10.0.0` in your `rsbuild.config.ts`.
- Replace the default import with the named one:

  ```diff
  -import useResizeObserver from 'use-resize-observer';
  +import { useResizeObserver } from 'use-resize-observer';
  ```

- The `use-resize-observer/polyfilled` entrypoint is removed: drop its alias from your Vitest configuration and stub
  `ResizeObserver` in your test setup instead, as jsdom doesn't implement it.
- The `onResize` callback now also receives the observed `ResizeObserverEntry` (`{ width, height, entry }`), and a
  measured size of `0` is reported as `0` instead of `undefined`.

See the [`use-resize-observer` migration guide](https://github.com/ZeeCoder/use-resize-observer/blob/master/MIGRATION.md)
for the complete list of changes.

### TanStack Query v5 is required

The Perses npm packages and the official plugins now require `@tanstack/react-query` `^5.105.0` as a peer dependency,
and the Perses application shares v5 with the plugins. Upgrade it in your plugin or in the application embedding Perses,
and follow the [TanStack Query v5 migration guide](https://tanstack.com/query/v5/docs/framework/react/guides/migrating-to-v5).
The most common changes are:

- Only the object signature is supported: `useQuery({ queryKey, queryFn })`,
  `queryClient.invalidateQueries({ queryKey })`, etc.
- Replace `keepPreviousData: true` with `placeholderData: keepPreviousData` (imported from `@tanstack/react-query`),
  `useErrorBoundary` with `throwOnError`, and `cacheTime` with `gcTime`.
- A query without data has the `status` `'pending'` instead of `'loading'`: check `isPending` to know whether its data is
  available. `isLoading` is now only `true` while the first fetch is running, so it stays `false` for a disabled
  query and for a query paused while offline.
- For mutations, `isLoading` and the `status` `'loading'` are renamed to `isPending` and `'pending'`.
- `QueryData.isLoading` of `@perses-dev/plugin-system` and the aggregated state returned by `useDataQueries` /
  `useDataQueriesContext` are renamed to `isPending`.

### ECharts v6 and Immer v11 are required

`echarts` is upgraded from `5.5.0` to `6.1.0` and `immer` from `^10` to `^11`. The Perses application shares these
versions with the plugins: bump them in your `package.json` (`"echarts": "6.1.0"`, `"immer": "^11.2.9"`) and rebuild
your plugin. ECharts v6 changes some defaults that can alter the rendering of your charts (e.g. gauge and heatmap): see
the [ECharts v6 upgrade guide](https://echarts.apache.org/handbook/en/basics/release-note/v6-upgrade-guide/) to restore
the previous behavior where needed.
