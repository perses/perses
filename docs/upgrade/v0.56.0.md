# Upgrading from v0.55.0 to v0.56.0

This document provides instructions for upgrading Perses specially when dealing with breaking changes. As Perses is a
rapidly evolving project, it's important to keep your installation up to date to benefit from the latest features and
improvements.

Then, upgrading Perses is also depending on your usage as Perses can be used in different ways (e.g. as a standalone
application, as a library, etc.). Therefore, the upgrade process may vary based on your specific use case.

## Perses application

### Deprecated configuration fields are removed

The following configuration fields were deprecated in previous releases and are now removed:

| Removed field                                         | Replacement                                                             |
|-------------------------------------------------------|-------------------------------------------------------------------------|
| `schemas`                                             | None, remove it from your config                                        |
| `ephemeral_dashboards_cleanup_interval`               | `ephemeral_dashboard.enable` and `ephemeral_dashboard.cleanup_interval` |
| `security.authorization.check_latest_update_interval` | `security.authorization.provider.native.check_latest_update_interval`   |
| `security.authorization.guest_permissions`            | `security.authorization.provider.native.guest_permissions`              |
| `plugin.archive_path`                                 | `plugin.archive_paths` (a list)                                         |

The configuration file is parsed strictly: **Perses refuses to start** if one of these fields is still present in your
configuration file. Update it before upgrading:

```yaml
# Before
schemas:
  panels_path: "schemas/panels"
  queries_path: "schemas/queries"
  datasources_path: "schemas/datasources"
  variables_path: "schemas/variables"
ephemeral_dashboards_cleanup_interval: 2h
security:
  authorization:
    check_latest_update_interval: 1m
    guest_permissions:
      - actions:
          - read
        scopes:
          - "*"
plugin:
  archive_path: /etc/perses/plugins-archive

# After
ephemeral_dashboard:
  enable: true
  cleanup_interval: 2h
security:
  authorization:
    provider:
      native:
        check_latest_update_interval: 1m
        guest_permissions:
          - actions:
              - read
            scopes:
              - "*"
plugin:
  archive_paths:
    - /etc/perses/plugins-archive
```

If you configure Perses with environment variables, the variables matching the removed fields are now **silently
ignored**. In particular, the guest permissions would no longer be applied, the ephemeral dashboards would no longer be
enabled, and the plugin archives would be looked up in the default folder. Rename them accordingly:

```txt
PERSES_EPHEMERAL_DASHBOARDS_CLEANUP_INTERVAL              -> PERSES_EPHEMERAL_DASHBOARD_ENABLE=true
                                                             PERSES_EPHEMERAL_DASHBOARD_CLEANUP_INTERVAL
PERSES_SECURITY_AUTHORIZATION_CHECK_LATEST_UPDATE_INTERVAL -> PERSES_SECURITY_AUTHORIZATION_PROVIDER_NATIVE_CHECK_LATEST_UPDATE_INTERVAL
PERSES_SECURITY_AUTHORIZATION_GUEST_PERMISSIONS_*         -> PERSES_SECURITY_AUTHORIZATION_PROVIDER_NATIVE_GUEST_PERMISSIONS_*
PERSES_PLUGIN_ARCHIVE_PATH                                -> PERSES_PLUGIN_ARCHIVE_PATHS_0
PERSES_SCHEMAS_*                                          -> (remove)
```

#### Go configuration API

If you use the Go package `github.com/perses/perses/pkg/model/api/config` directly, the corresponding types and fields
are removed as well:

- The type `Schemas` and the constants `DefaultPanelsPath`, `DefaultQueriesPath`, `DefaultDatasourcesPath` and
  `DefaultVariablesPath` are removed, as well as the field `Config.Schemas`.
- The field `Config.EphemeralDashboardsCleanupInterval` is removed. Use `Config.EphemeralDashboard` instead.
- The fields `AuthorizationConfig.CheckLatestUpdateInterval` and `AuthorizationConfig.GuestPermissions` are removed, as
  well as the method `AuthorizationConfig.Verify()`. Use `AuthorizationConfig.Provider.Native` instead.
- The field `Plugin.ArchivePath` is removed. Use `Plugin.ArchivePaths` instead:

  ```go
  // Before
  config.Plugin{ArchivePath: "plugins-archive"}

  // After
  config.Plugin{ArchivePaths: []string{"plugins-archive"}}
  ```

## Plugin developer

### React 19 is supported

The Perses npm packages (`@perses-dev/client`, `@perses-dev/components`, `@perses-dev/plugin-system`,
`@perses-dev/dashboards`, `@perses-dev/explore`) and the official plugins now accept `react` and `react-dom`
`^18.3.0 || ^19.0.0` as peer dependencies. Widen the React peer dependencies and the Module Federation `requiredVersion`
of `react` and `react-dom` of your plugin the same way to support both versions.

### The Perses application runs on React 19

The Perses application now runs on React 19 and shares `react/jsx-runtime` with the plugins as a singleton, alongside
`react` and `react-dom`. A plugin bundling its own React 18 JSX runtime crashes on a React 19 host: add
`react/jsx-runtime` to the Module Federation `shared` configuration of your plugin and rebuild it:

```ts
shared: {
  react: { requiredVersion: '^18.3.0 || ^19.0.0', singleton: true },
  'react/jsx-runtime': { requiredVersion: '^18.3.0 || ^19.0.0', singleton: true },
  'react-dom': { requiredVersion: '^18.3.0 || ^19.0.0', singleton: true },
  // ...
},
```

In dev mode (e.g. `percli plugin start`), the default JSX transform imports `react/jsx-dev-runtime`, which the Perses
application doesn't share: the plugin then bundles its own React 18 development runtime and crashes the same way. With
Rsbuild, compile JSX to `react/jsx-runtime` in dev mode as well:

```ts
pluginReact({
  reactCompiler: { target: '18' },
  swcReactOptions: { development: false },
}),
```

Keep compiling your plugin with the React Compiler target `18` so it still runs on React 18 hosts (e.g. applications
embedding Perses).

### `@mui/system` is a peer dependency of `@perses-dev/components`

Install `@mui/system` (`^6.1.10`, matching your `@mui/material` version) if your package manager doesn't install peer
dependencies automatically.

### `use-resize-observer` v10 is required

`use-resize-observer` is upgraded from `^9` to `^10` (v9 doesn't support React 19). The Perses application shares v10
only with the plugins (`requiredVersion: '^10.0.0'`), so a plugin still built against v9 can no longer use it. Upgrade it
in your plugin:

- Bump `use-resize-observer` to `^10.0.0` in your `package.json` and, if your plugin shares it with Module Federation,
  set its `requiredVersion` to `^10.0.0` in your `rsbuild.config.ts`.
- Replace the default import with the named one:

  ```diff
  -import useResizeObserver from 'use-resize-observer';
  +import { useResizeObserver } from 'use-resize-observer';
  ```

- The `use-resize-observer/polyfilled` entrypoint is removed: drop its alias from your Vitest configuration and stub
  `ResizeObserver` in your test setup instead, as jsdom doesn't implement it.
- The `onResize` callback now also receives the observed `ResizeObserverEntry` (`{ width, height, entry }`), and a
  measured size of `0` is reported as `0` instead of `undefined`.

See the [`use-resize-observer` migration guide](https://github.com/ZeeCoder/use-resize-observer/blob/master/MIGRATION.md)
for the complete list of changes.
